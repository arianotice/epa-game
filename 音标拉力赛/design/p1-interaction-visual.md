## §0 结论摘要与硬约束

### 0.1 一句话结论

用户三项新诉求（车速慢 / 不丝滑、NPC 扎堆、可见分叉）里，**判定域的数学模型早已完备，缺的全在视觉域**：`SNAPSHOT_KEYS` 白名单（`scene3d-model.mjs:64-66`）未投影 `pickups`、分叉 `flare`、跳跃段数；`buildSceneFrame()`（:156）只产单条 `road[]` ribbon（`roadStyle:"solid"`、`m8MirrorGate:false`，:301-302）；`lift`（:209）把「滞空剩余秒数」误当高度。

因此本轮**不是优化，是「从零补」**：3 层 3D 几何（石头 / 分叉 / 跳跃）+ 1 层白名单扩展 + 1 层双循环相位对齐，且**只动视觉层**——判定绝对里程、答案域零触碰。

三个「最省改动」落点（本轮实测发现，直接决定工程代价）：
- **`scene3d.jsx:257` 已预留 y 通道**：`obj.group.position.set(k.x, k.lift || 0, k.z)` → 跳跃修复**只需改 `scene3d-model.mjs:209` 的 lift 公式 + `KART_KEYS`，`scene3d.jsx` 零改动、零新增 mesh**。
- **`buildSceneFrame()` 已预留 `opts.worldScale`（:162）与 `opts.aheadM/behindM`（:163-164）** → 视觉缩放有现成注入口，**无需改函数签名**；但直接调 `WORLD_SCALE` 会等比撑大路宽 / 圈长 / 雾距（见 §2.3 美术侧风险），必须配冻结常量或改用环境流速增益。
- **`SNAPSHOT_KEYS` 已含 `time`（:65）与 `span`（:65）** → NPC 人味抖动、分叉 flare 的相位源现成可用，**无需为这两项扩展白名单**。

## §1 现状测绘（文件:行号 + 函数名 + 数据结构）

### 1.1 产物链与三条互不共享 dt 的循环

```
js/scene3d.jsx + js/scene3d-model.mjs
        │  js/build-p1.mjs（预构建）
        ▼
assets/p1/scene3d.js  ← 主站动态注入的 IIFE，线上 renderMode=3d
```

三条循环**无共享 clock、无共享 dt、无相位对齐**（`scene3d.jsx:58` 自述 `rafSource: "r3f useFrame + 独立 mount-decision rAF（与 main.js frame() 分离）"`）：

| # | 循环 | 落点 | 职责 | dt |
|---|---|---|---|---|
| L1 | `main.js frame(now)` | `:1068`，`:1069` `dt=Math.max(0,Math.min(0.033,(now-last)/1000))`，`:1094 race.update(dt,input)`，`:1143/:1183 requestAnimationFrame` | **判定权威**（odo / t / 门 / 石头 / cheer）+ 2D `render(ctx)` :1119 + `syncCheer` :1141 | 有，但 clamp 0.033 |
| L2 | R3F `useFrame()` | `scene3d.jsx:382-395` | 每帧 `camera.fov/position/lookAt` + `world.update(f)` + `publish()` | **不接 dt** |
| L3 | `decisionLoop()` | `scene3d.jsx:486-501`（`:499`、`:501` 两次 rAF） | 仅决策「3D 何时挂载」 | 无 |

`useFrame()` 每帧直接 `readFrame()` 读**当前** `race.state` 快照，`world.update(f)`（`scene3d.jsx:230-267`）对 mesh **直接 `position.set` / `rotation.y` 赋值，无任何插值 / 缓动 / 固定步长**（:257 三车、:245 虚线、:263 门、:266 起终点门）。

### 1.2 相机 / 投影：相机不动，是世界在重算

- `CAMERA_PRESET`（`scene3d-model.mjs:25`）：`distanceM:8, heightM:3.6, pitchDeg:18, lookAheadM:9`；`fov375:78 / fov320:74 / fovWide:60`，由 `cameraFovFor()`（:133-134，`w<=340` 取 320）选取。
- `buildSceneFrame()` :254-266：相机**固定在 `[0, 3.6, 8]` 米制**，`look = pos + forward·lookAheadM`，`vanishingPointY = tan(pitch)/tanHalf`。
- 视觉「滚动」**不是相机沿世界跑**，而是 `road[]` / `karts[]` / `gates[]` 按 `t0` 的**局部坐标系重算**：`s = track.sample(wrap01(t0 + dzM/(L*scale)))`（:181）。`odoEstM=(lap+t0)*L*scale`（:175）仅为 QA 可观测信号，非读取判定 odo。

## §2 「太慢 / 不丝滑」根因与视觉层方案

### 2.1 数值根因（工程线 R1 实算，本报告采纳）

视觉速度 = 玩家 `t` 每秒推进量 × `L*scale` = `DIFFICULTY.speed × WORLD_SCALE`：

```
speed=260 unit/s × 0.008 m/unit = 2.08 m/s   （车长 1.6m → 仅 1.3 车身 / 秒）
speed=300 unit/s × 0.008 m/unit = 2.40 m/s
```

小学生赛车预期约 5–10 车身 / 秒，差 4–8 倍。乘数链 `BOOST.mul=1.48` / `TURBO.mul=1.92` / `SLOW.mul=0.54` / `ROCKET.mul=1.55`（`config.js:224-227`）只在 `speedNow()`（`race.js:183`）放大 `odo`，不改变尺度感。

**「不丝滑」最可能根因（按权重排序）**：

| 权重 | 根因 | 证据 |
|---|---|---|
| **主因 1** | **双循环无插值 / 相位对齐**：L1 判定 `frame()` 与 L2 R3F `useFrame()` 各自采样不同时刻的 `race.state`，3D 直接 `position.set` 到当帧目标值，帧间位置是阶跃 | `main.js:1068/:1094`；`scene3d.jsx:382`（不接 dt）、`:257`（直接 set） |
| **主因 2** | **dt clamp 0.033 截断判定时间**：掉帧 >30ms 时判定只推进 0.033s，但 R3F 帧仍按当前 `race.state` 采样 → 「判定慢 / 视觉跳」相位撕裂 | `main.js:1069` |
| 主因 3 | **视觉绝对速度过低**（2.08 m/s），路面虚线 / 路肩 / 雾中远景流速过慢，主观「慢 + 一顿一顿」被放大 | `scene3d-model.mjs:20/:181` |
| 次要 | `roadGeo` 每帧重写 49×2 顶点 + `publish()` 每帧三车 Box3 八点投影 + 2D `render(ctx)` 与 `drawConfetti()` 全屏 clear 仍在跑，CPU 帧时抖动 | `scene3d.jsx:199/:279`；`main.js:729/:1119` |
| 次要 | L3 `decisionLoop()` 独立 rAF 与 L1/L2 无同步 | `scene3d.jsx:486-501` |

**结论**：不是 drawCall 抖动（71 恒定），也不是相机抖动（相机固定），是**「判定时间被 clamp + 视觉位置无插值的相位撕裂」×「2.08 m/s 的低流速」**叠加。

### 2.2 提速方向：只动视觉层，绝不改 `DIFFICULTY.speed`

改 `DIFFICULTY.speed`（`config.js:36/:46`）会连锁撞判定绝对里程、完赛时间、`≤180s` 约束、写死 260/300 的断言与 `forkSpan()`（`config.js:301`），**不可取**。工程线「改视觉层比改判定安全」的方向成立。

但美术侧必须点明一个**会破坏已拍板构图的陷阱**：

### 2.3 ⚠ 美术侧风险：`WORLD_SCALE` 不是纯速度旋钮

`scale` 在 `buildSceneFrame()` 里同时驱动四组量：

```js
// scene3d-model.mjs
const scale = opts.worldScale ?? WORLD_SCALE;            // :162
s = track.sample(wrap01(t0 + dzM/(L*scale)));            // :181  前方采样 t 窗口
w = roadHalf * scale;                                    // :188  路面半宽（4.16m）
x,z = toLocal(..., scale);                               // :182-183 世界坐标
dzM = wrapHalf(ti-t0) * L * scale;                       // :203  车 / 门相对里程
lapLengthM = L * scale;                                  // :245  圈长 154.036m
```

简单把 `WORLD_SCALE` 乘 k，会**等比撑大**路宽（4.16m→4.16k m）、圈长、前方弯道曲率、雾距，而**车体是固定米制**（`KART_BOX` :60 `lengthM:1.6 / widthM:0.9 / heightM:1.05`）、相机也是固定米制（3.6 / 8 / 9）。结果：车相对路面「缩小」、路变宽、消失点漂移 —— **直接违反 `p1-3d-art-spec.md` §1.3 换算表 / §2.3 构图校验 / §5 六维阈值**，且 24px 黑剪影、S≤45%、细节随距衰减全部需重验。

**给工程线的两个可选落点（v1.2：方案 B 已由主理人采纳为 P1 提速默认值，见 §9 裁决记录）**：

- **方案 A（工程线方向，谨慎采纳）**：`opts.worldScale` 注入视觉放大值，**同时冻结构图相关米制常量** —— 把 `roadHalf*scale`（:188/:226）、`KART_BOX`（:60）、`CAMERA_PRESET`（:25）、`FOG_DENSITY`（:246）改为**固定米制字面量**，只让 `L*scale`（:181/:203/:220/:236）增大。代价：白名单换算层出现「两套尺度」，需补单测；且**必须重出 §1.3 换算表并复验六维阈值**。
- **方案 B（美术推荐，几何零漂移）**：**判定 t 与视觉「环境流速」解耦**。车体 / 门位 / 分叉 / 石头**严格绑定判定 t**（零漂移，保证「开进正确车道」画面与判定一致），另引入 `VISUAL_FLOW_GAIN` 只放大**纯环境元素的滚动相位**：路面中央虚线（`scene3d.jsx:245`）、路肩标记、雾中远景、路面粒子、路牌后退速率。速度感来自「环境流过得多快」，而非整车位移 —— 这是竞速游戏最常用且不损判定一致性的做法。`opts.worldScale` 保持 0.008 不动，**六维阈值 / 构图校验零复验**。

> **✅ 已拍板（v1.2）：方案 B 采纳为 P1 提速默认值** —— 车体 / 门位 / 分叉 / 石头严格绑定判定 `t`（几何零漂移、六维阈值与构图校验零复验），另引入 `VISUAL_FLOW_GAIN` 只放大纯环境元素（中央虚线 / 路肩 / 雾中远景 / 路面粒子 / 路牌后退）的滚动相位。A 会把已锁定的美术基线整体重标，性价比低，仅留作备选记录。
>
> 美术侧补充判据（配合 §6.1 NPC 速度感）：`VISUAL_FLOW_GAIN` 是**全局单一标量**，作用于路面与全体车辆共享的环境参照物，不单独给玩家加、不给 NPC 减，从根上保证「NPC 不明显慢于玩家」在视觉上成立。

### 2.4 「两循环插值 / 相位对齐」最小改动点

**不新增 rAF、不新增 mesh、不改 drawCall 分组**，只在既有 L2 `useFrame()` 内加一步阻尼：

1. L1 `frame()` 仍是判定权威；`race.state`（含 `karts[].t/lateral`、`gates`）由 L1 推进。
2. L2 `scene3d.jsx:382 useFrame((state, delta) => ...)` 启用 R3F 自带的 `delta`，维护 `visualState = { prev, curr }` 与共享 `alpha`；`world.update(f)` 升级为 `world.updateInterpolated(f, delta)`：
   - 对 `karts[].x/z/rotation.y`、`road[]` 顶点、`gates[].x/z` 做**阻尼 lerp**（`λ≈12–18 /s`，或 `alpha = 1-exp(-λ·delta)`），而不是直接 `position.set` 目标值。
   - 关键：**阻尼只作用于已有 transform**，不改 mesh 数量 / 材质数 / drawCall 分组 → **63 mesh / 71 drawCalls 不变**。
3. dt clamp 的相位撕裂由「视觉侧对目标值做阻尼」自然吸收：即使 L1 一帧截断，L2 也会平滑趋近，不再阶跃。
4. `publish()`（:279）仍读阻尼后的 f，QA 断言不变。

> 硬红线：**车体视觉 t 绝不可脱离判定 t**。任何「让车看起来跑更快」的独立相位偏移都会使分叉门位、石头位置与画面脱节，直接破坏「把车开进正确那条」的核心交互（ADR-2）。提速只能来自 §2.3-B 的环境流速。

### 3.6 石头骤减到 ≤2 颗/局后，如何仍「沿途有障碍」而不空旷（v1.2 新增）

**问题**：判定侧把 16 颗石头压到 ≤2 颗/局（§3.1 用户裁决），3D 主形态若只画这 2 颗，赛道会从「藏宝图探险」退化成「空跑道」——`aheadM=48 m` 前向带里绝大多数帧看不到任何障碍，与「四区探险 + 有趣味但不低幼」的世界观冲突。**但绝不能偷偷多画可碰撞石头**（会破坏 ≤2 次撞击的硬验收、且违反判定唯一真值）。

**解法：把「障碍感」从「碰撞体」拆成「三层视觉密度」，只加不参与判定的中性装饰**（全部只读 `track.sample()` / `zone`，不进 `pickups` 白名单、不写 `state` → B8/ADR-2 视觉侧零触碰）：

| 层 | 内容 | 参与判定 | 视觉职责 |
|---|---|---|---|
| **L1 真障碍（≤2 颗/局）** | §3.3 的石头几何 + 描边 + 地面警示光圈 | ✅ 是（唯一可撞） | 保留「必须跳」的紧张感；因稀有，反而更该做足 §10.2 的起跳标线与预告 |

### 3.6b L2 与 L1 的视觉可区分性硬要求（v1.4 新增 · 主理人一致性风险裁定）

> **裁定依据**：设计线 v1.1 否决了「石头照旧多、只把碰撞次数封顶 2」的备选，理由是**封顶后的石头会变成「撞了也没事」的假障碍，让小学生学到错误规则（欺骗反馈）**。L2 技术上不进 `pickups` 白名单 / 不进碰撞逻辑，与它不同；**但只要 L2 在画面上长得像 L1 真障碍，玩家仍会起跳、跳了却没有任何反馈** —— 这就是同一类「习得错误规则」问题。故可区分性不是加分项，是**采用 L2 的前置硬要求**。

**H1 · 造型 / 色彩 / 材质一眼可分（防「跳了没反馈」）**：
- L2 **造型类别**必须是带明显人工器物 / 平面标识轮廓的地图母题（刻纹路碑、发光矿石簇、宝箱碎片、木箱、小旗、蕨丛），**严禁圆石 / 半埋石 / 碎石堆 / 与 L1 同款的低 poly 多面体**（L1 = `Icosahedron/Dodecahedron` 半埋圆石，§3.3）。
- L2 **不沿用 L1 材质语言**：L1 是暖灰 `#8a7355` + 墨色 `EdgesGeometry` 描边（§3.3）；L2 用平面化 / 低对比的 `--ink-soft` 淡影 + `--gold-deep` 描线细节，**不做立体描边闪烁、不做地面警示光圈、不做呼吸动效**（这些是 L1 的「必须跳」信号，§3.5）。
- **24px 黑剪影可辨**（六维阈值）：把 L1 / L2 缩到 24px 纯黑剪影，形状必须不同类（圆钝块 vs 竖立碑 / 旗帜 / 箱形），色弱玩家不靠颜色即可分辨。

**H2 · 位置物理隔离（防「引发跳跃意图」）**：
- L2 **绝不放在车道内或车道边缘可及处**：横向 `|lateral| ≥ 0.85`（L1 车道内 `≤0.66`，`race.js:134`；玩家可及 `|lateral|≤1`），即严格在 `roadHalf` 外缘之外的路肩 / 路外；**玩家无论怎么打方向都碰不到**，从空间上断了「要不要跳」的犹豫。
- L2 不进 `pickups` 白名单、不进 `snapshot3d()`，3D 层只读 `track.sample(t)` + `snap.zone`（§3.2 合规逻辑同构）。

**H3 · 零反馈契约（写死，防「欺骗反馈」）**：
> **L2 绝不触发 `scanPickups()`（`race.js:566-595`）、绝不产生欢呼词 / 局部小纸屑（§10.4）、绝不产生惩罚做题（`race.js:588-592` `openQuiz("rock")`）、绝不产生 `state.ribbonT` / `state.shake` / `audio.bump()` 等任何碰撞反馈。** L2 是纯 3D 装饰几何，没有任何游戏状态副作用。

**判据（自动化 + 人工过眼，供质量线选）**：
- **自动化**：`state.pickups` 中 `kind==="rock"` 的条数一局内恒 ≤2（§3.1）；L2 不产生任何 `pickups` 条目 → 该计数与画面中圆石数量一致；静态扫描 `scene3d.jsx` / `scene3d-model.mjs` 中不含 L2 相关的 `cheer(` / `openQuiz(` / `ribbonT` / `shake` 写入（B8 同源，§0.3-3）。
- **人工过眼**：给小学生看 10 秒 3D 录屏，问「哪些东西要跳过去」——**指向 L2 的次数必须为 0**；缩到 24px 黑剪影后 L1/L2 能分类；任意帧 L2 都在路肩外、无警示光圈、无立体描边。

**H4 · 明确退路（允许直接不采纳 L2，实现层不得自行发挥）**：
> 若上述 H1–H3 任一条无法保证（例如实机上 L2 仍被误认为障碍、或美术资源不足以做出一眼可分的造型），**允许直接不采纳 L2，赛道只保留 L1 真障碍（≤2 颗/局）+ L3 宝石（10 颗）+ 既有路面虚线 / 四区主题色 / 纸雾纵深**。**宁可赛道清爽，也不要误导**。此退路是主理人明确批准的选项，与「≤2 颗石头」不冲突；采用时 §7 的 L2 InstancedMesh 与 +1 drawCall 预算自动取消（预算更松，不破 ≤72 drawCalls）。**实现层不得自行把 L2 换成别的「看起来像障碍」的装饰来绕开本要求** —— 要么满足 H1–H3，要么走 H4 不用。

**性能**：L2 用 **1 个 `InstancedMesh`**（与 §3.3 石头/宝石各 1 个并列，共 3 个 InstancedMesh），实例数可给到十几而不增 drawCall；**≤72 drawCalls 的照准预算不变**（§7 / §9-3）。L2 几何走 `track.sample(t)` 的确定性锚点（如每 `0.04 t` 一个、按 `t` 哈希选样式），**零随机、可单测、可复现**。（若走 H4 退路，本节整块不实施。）

**可过眼验收（v1.4 收紧）**：
1. 采用 L2 时：任意非分叉帧，`aheadM` 前向带内**至少可见 1 个 L2 装饰**（不空旷）；走 H4 退路时本条不适用。
2. **H1–H3 全过**：L1 与 L2 **造型类别一眼可分**（不是「只靠位置/光圈」）、L2 在 `|lateral|≥0.85` 路肩外、L2 没有任何欢呼/纸屑/惩罚/碰撞反馈；色弱玩家靠**剪影形状 + 位置**而非颜色区分（A11Y）。
3. 一局内可撞石头仍 **≤2 次**，L2 零碰撞（QA 可数 `state.pickups` 中 `kind==="rock"` 的条数）。
4. **小学生不误跳**：10 秒过眼测试中指向 L2「要跳」的次数为 0（H3 人工判据）。

> 边界重申：本节所有内容都是**纯 3D 装饰几何**，不新增 `pickups` 条目、不改 `taken`、不写 `odo/lateral/g.line`（§0.3-1 视觉侧铁律、§0.3-3 B8）。判定侧「≤2 颗」由工程线在 `buildField()` 实现，本文档只保证减量后画面不塌、且不教错规则。

## §5 缺口三：3D 跳跃高度（从零 / 修正）

### 5.1 现状：几乎不可见，且一段 / 二段长得一样

- `scene3d-model.mjs:209`：`lift: Math.max(0, Number(k.air) || 0) * scale`。`k.air` 是**剩余滞空秒数**（`race.js:650` `airMax=0.5, air=0.5`；`:655` `airMax=0.74, air=0.74`），**不是高度**；`×0.008` → 最高 `0.5×0.008 = 0.004 m`（R1 实算 0.004m），相对车高 1.05m 完全不可见。
- `KART_KEYS`（:67-69）**只有 `air`**，缺 `hop` / `airMax` / `dashLeft` → 3D 层**无法区分单跳与二段跳**。
- `scene3d.jsx:257` 已预留 `k.lift || 0` 的 **y 通道**（重要：这是修复零改动的落点）。

### 5.2 白名单扩展面（最小、中性）

```js
// scene3d-model.mjs:67-69 —— 建议仅追加 2 个中性动作量
export const KART_KEYS = Object.freeze([
  "id","kind","t","lateral","drift","boost","turbo","air","yaw","hop","airMax",
```

- `hop`（1/2）、`airMax`（0.5/0.74）是**玩家动作量，非答案域**；`dashLeft` 可不进白名单（「保持前行」由 §5.4 的视觉约束保证，不需要数值）。
- 合规：只读投影，3D 层不写回 → B8 / ADR-2 不命中；`GATE_KEYS` 不动 → 零泄露保持。

### 5.3 两级高度量级（v1.2 按「单跳必过」重校准，单位必须是「米」）

**先定石头的可见高度 `h_rock`（这是校准的锚，原稿缺这一环）**：§3.3 的 `IcosahedronGeometry(r≈0.36–0.48)` 若整颗外露、球心贴地，可见高度达 `2r ≈ 0.72–0.96 m`，**比原单跳峰值 0.45 m 还高** —— 判定域只看 `air>0.05`（`race.js:578`）算「跳过」，视觉上却是车底从石头里穿过去。这就是 P0「一次点击跳不过」在视觉侧的孪生病灶。

⇒ **石头改为半埋低矮石块**：几何半径保留 `r≈0.36–0.48 m` 做横向体量，但埋入路面 55–65%，**露出的可见高度 `h_rock ≈ 0.30–0.34 m`，取 0.32 m 为基准**；顶面不对称凸起/裂纹仍保留（24px 剪影识别）。半埋同时强化「地上蹦出一块石头」而非「路上立着一块碑」，更贴藏宝图语汇。

```js
// 建议替换 scene3d-model.mjs:209（v1.2：lift 与判定 air 解耦，纯视觉抛物线）
const H_ROCK = 0.32;                                                  // 与 §3.3 几何共用常量，半埋后可见高度
const airMax = Math.max(0.001, Number(k.airMax) || 0.5);
const p = Math.max(0, Math.min(1, 1 - (Number(k.air)||0) / airMax)); // 0→1 滞空进度
const peak = (Number(k.hop) === 2) ? 0.85 : 0.55;                     // 米：单跳「刚好过」/ 二段「从容过」
const lift = peak * 4 * p * (1 - p);                                  // 抛物线单峰
```

| 段 | 峰值（v1.2） | 对 `h_rock=0.32 m` | 相对车高 1.05 m | 语义 |
|---|---|---|---|---|
| **单跳 `hop=1`** | **0.55 m**（原 0.45） | **1.7×，净余量 +0.23 m** | 0.52× | **「完美刚好」跳过**：车底明显越过石顶，一眼看出过去了；不夸张、不「起飞」 |
| **二段跳 `hop=2`** | **0.85 m**（原 0.80） | 2.7×，净余量 +0.53 m | 0.81× | 「更高余量 / 炫技」，与单跳差 **0.30 m（≈0.29 车高）**，一眼可分 |

> **硬约束（可过眼验收 · v1.3 终裁）**：① **单跳这一级就必须能过** —— **单跳峰值 − `h_rock` ≥ 0.20 m**，且在 §10.2 的判定帧处 `lift > h_rock`（「车底在石顶之上」必须成立），小学生一眼看出「跳过去了」；**有效窗由工程侧按 `air`（≈0.45 s / 117–135 2D unit）保证，与双击无关**；② **二段峰值 − 单跳峰值 ≥ 0.25 m** 保证两级可区分，二段跳只是更高余量、**不作通关门槛**；③ 二者均 ≤ `0.945 m`（车高 1.05 m 的量级上限），避免「起飞」失真、不低幼。实机可在 `0.50–0.60 / 0.80–0.90 m` 微调，但三条硬约束不得破。
> **关键解耦**：判定域的「跳过」只看 `air > 0.05`，与 `lift` 数值无关 → 视觉侧可自由把 `lift` 从当前 0.004 m 抬到 0.55/0.85 m，**不改任何判定、不新增 mesh**（`scene3d.jsx:257` y 通道现成）。这也意味着「单跳必过 100% 成功」由判定侧 `hopWindow` 保证，视觉侧只负责让它**看起来**成立。

**两级视觉区分（不新增 mesh，全部走已有 `k.lift` / `rotation` / 阴影）**：
- **单跳**：单峰拱形，峰值 0.55 m；接地阴影（复用已有 scale）收缩一次。
- **二段跳**：`hop===2` 时在 `p≈0.5` 处叠加**第二次抬升脉冲**（双峰曲线，峰值 0.85 m），形成「顿一下再往上」；车尾一小簇纸屑 / 墨点（≤3px 等效抖动）；阴影二次收缩、离地间隙明显更大。
- 依据 `race.js:659-661`：二段跳附带 `dashLeft=140`、`jumpCd=0.9`，视觉上可给一次极轻前倾（`rotation.x` ≤2°）强化「再冲一下」。
- **A11Y**：两级差异同时靠**高度 + 阴影离地间隙 + 是否有第二峰**三重编码，不只靠颜色/高度单一线索；动敏可关时仍保留高度差（静态可辨）。

### 5.4 「保持前行」如何视觉成立 + 与 `hold` 冻结区分

- **保持前行**：`dashLeft=140` 在 `race.js:293-296` 以 `min(dashLeft, 900*dt)` 消耗并 `odo += d` → 判定层本就不停车。3D 侧**不得对 `karts[].z` 做任何减速插值或回拉**；§2.4 的阻尼 lerp 只吸收相位抖动，不改变平均前进速度。
- ⚠ **`hold` 冻结**（`race.js:631-641`，`state.decide.phase==="hold"` 时 3 秒整体冻结 odo、并 `pressRivals()`）在画面上也是「车不动」，**必须与跳跃态区分**：
  - `hold` 态：HUD 给「听音中」标识 + 画面极轻去饱和 / 纸带定格（≤3px 等效），明确「这是等待，不是可操作」。
  - 跳跃态：车身明显抬起（**单跳 0.55 / 二段 0.85 m**，§5.3）+ 阴影离地 + 二段前倾，**绝不去饱和**。
  - 二者一个「贴地静止 + 等待标识」、一个「离地上冲」，小学生不会误判。

**⚠ v1.2：单跳必须是「一次点击即完整成立」的闭环，二段跳不得成为门槛**（用户最终拍板）：
- HUD「可跳跃态」提示（§6.3）只写「点一下跳 / 空格跳」，**不出现任何「再点一次」「双击」字样或二段跳专属提示**；否则会诱导小学生以为必须双击才能过石头。
- 成功跳过的欢呼 + 纸屑（§10.4）在**单跳**成功时就要完整触发一次，不区分 `hop===1 / 2`，避免「单跳没奖励、二段才给」的隐性门槛。
- 二段跳的额外收益只体现在**视觉余量更高（0.85 m）+ 冲刺前倾**，属「可选炫技」，不影响能否过关、不影响判定成败。

#### 6.1b NPC「速度感」+ 不扎堆：配套落点与可过眼判据（v1.2 新增）

**症状根因**：`baseMul()`（:177）给 NPC 仅 `a=1.02 / b=1.008`，且 `pressRivals()`（:397）会把它们拉回玩家附近 → 判定上就几乎同速同位置，视觉侧再怎么加抖动也像「陪跑脚本」。用户明确要「不龟速、不扎堆、看起来像其他玩家在玩」。

**判定侧（工程线，ADR-2 已放行）**：
- **不得明显慢于玩家（v1.3 终裁统一口径）**：NPC 瞬时速度须满足 **`v_i ≥ 0.94 · v_player_now`**（设计线 N8 / 质量线 / 工程规格已统一到此值，**更早倍数口径作废**）。实现上 `baseMul` 抬到 `≈0.96–1.06` 区间并给缓慢正弦起伏（不是恒定 1.008），且须在玩家吃 `BOOST/TURBO`（`config.js:224-227` 乘数 1.48/1.92）时同步跟随，保证任何时刻都不跌破 0.94×、既不龟速也不瞬间套圈；
- **错峰起始里程**：a / b 起跑 `startT` 各自错开（现 `:38-41` 三车同为 `0.02`），并按 `id` 设不同相位；
- **各自 `laneTarget`**：a 偏左、b 偏右，只在分叉/超车时缓动换道，`pressRivals()` 改为「软跟随」而非硬拉回同一 `t`。

**视觉侧（本文档范围，只读）**：
| 手法 | 实现 | 约束 |
|---|---|---|
| **同环境流速** | 方案 B 的 `VISUAL_FLOW_GAIN` 是全局标量，路面虚线 / 路肩 / 远景对**三车一视同仁** → NPC 与玩家共享同速的「地面在后退」参照，视觉上不会「玩家在跑、NPC 在滑」 | §2.3 已拍板；不单独给 NPC 缩放 |
| **轮尘 / 尾迹** | 三车各挂同规格的极淡纸屑尾迹（复用现有粒子或 `boosting` 材质层），强度与各自速度正相关；**NPC 不得无尾迹** | 0 新增 drawCall（并入已有 InstancedMesh），≤3px 抖动 |
| **人味抖动 + 换道摆动** | §6.1 表中 yaw 正弦 / lateral 低频缓动，且 a / b **相位不同**（用 `k.id` 做相位种子），避免「同步镜像」 | `snap.time` 确定性纯函数 |
| **身份配色** | 蓝+Q / 红 / 绿 + Q 标差异（:202），让三车在 24px 剪影下可区分 | A11Y 不靠红绿区分左右车道 |

**可过眼判据（QA / 实机目测 · v1.3 终裁口径 `0.94×`）**：
1. **不龟速（`v_i ≥ 0.94 · v_player_now`）**：任一 10 s 连续观察窗内，两辆 NPC **速度始终 ≥ 玩家当前速度的 0.94×**、**且始终留在 `aheadM=48 / behindM=10` 可视带内**，不出现「被永久甩出画面」或「贴着玩家车尾不动」；玩家触发 `BOOST/TURBO` 的瞬间 NPC 也不得被拉开到明显慢一档（§6.1b 同步跟随）；
2. **不扎堆**：任意时刻三车在画面上**占据 ≥2 条可辨车道或 ≥1 个车身长的纵向错位**，不出现两车轮廓长时间（>1.5 s）重叠成一团；
3. **像真人在玩**：a / b 的换道、摆动**不同步**，且至少各发生 1 次可见换道/超车；尾迹三车都有；
4. **速度感一致**：三车相对路面参照物的后退速率目测同量级（不出现某车「飘着走」）。
> 判据 1–4 均可用 `buildSceneFrame()` 输出的 `karts[].x/z/dzM` 做 Node 单测断言（纯函数、可复现），与 §2.4 的插值相位对齐同批验。

- **v1.4 `seq` 语义写死（主理人确认口径）**：`seq` 全局单调递增，**每次 `cheer()` 调用（判门命中 / 成功跳过）都 +1**。所谓「两类触发源共用 `c.seq`」= **判门命中欢呼与成功跳过欢呼各自每次恰好播一次，seq 全局递增、互不吞掉**；**绝不是「全局同时只允许一个欢呼」，两类不互斥**。`cheerShown !== c.seq` 的判据只负责「同一触发不重播」，**不得**被用来抑制另一类触发或把两类合并成一个。验收：连续两次判门命中各播一次、连续两次成功跳过各播一次、判门后紧接着成功跳过（或反之）**两次都播**、连续同词也各播一次。

### 10.2 单跳峰值 × 石头高度关系：让小学生「一眼看出跳过去了」

**核心矛盾（v1.2 诊断）**：判定域用 `air>0.05` 判成功，与视觉高度完全解耦；而当前视觉 `lift` 仅 0.004 m、石头若整颗外露高 0.72–0.96 m → 画面上是「车从石头里穿过去」，玩家自然觉得「没跳过去」。**所以「跳不过」既是判定 bug，也是视觉谎言，须两侧同修。**

| 量 | 值（v1.2 定稿 / v1.3 终裁确认） | 理由 |
|---|---|---|
| 石头可见高度 `h_rock` | **0.32 m**（半埋，§3.3） | 半埋 55–65%，露出 0.30–0.34 m；比整颗外露矮一半，让「越过」在画面上成立且不显笨重 |
| **单跳峰值 `lift₁`** | **0.55 m —— 这一级就必须能过** | `lift₁ − h_rock = 0.23 m ≥ 0.20 m` 硬约束 → 车底明显在石顶之上、`0.52×` 车高不夸张；**单跳即保证「小学生一眼看出跳过去了」，不依赖第二击** |
| 二段峰值 `lift₂` | **0.85 m —— 只是更高余量** | `lift₂ − lift₁ = 0.30 m ≥ 0.25 m` → 两级一眼可分；净余量 0.53 m = 可选炫技，**不作通关门槛** |
| 上限 | ≤ `0.945 m`（车高 1.05 m 的量级上限） | 避免「起飞」失真、不低幼；与 NPC 速度 `0.94×` 口径无关，勿混 |

> **v1.3 终裁口径**：**「单跳必过」为硬验收** —— 单跳峰值必须明确高过石头、让小学生一眼看出「跳过去了」；**有效窗由工程侧按 `air`（单跳 `air=0.5 s` → 有效 ≈0.45 s / 117–135 2D unit ≈ 0.94–1.08 m，见 §3.4 / §10.1）保证，与双击无关**。二段跳只是更高余量、不作通关门槛。

**「完美刚好」的可过眼判据（QA 可截图断言）**：
1. **顶点帧**：玩家车底与石顶之间可见 ≥0.20 m 的**纸色路面间隙**（车底在石顶之上），无穿插；
2. **进窗帧**（`|Δodo|=78` 附近）：`lift > h_rock` 仍成立 → 判定算「跳过」的那一刻，画面也确实在石头上方（视觉与判定同相位，杜绝「算过了但看着撞了」）；
3. **落地帧**：`air===0` 时车已完整越过石头纵向位置，无「半截卡在石头里」；
4. **单跳 = 完整闭环**：一次点击后上述 1–3 全部成立 + 欢呼词 + 局部小纸屑各触发一次（§10.4）。

**提前可见距离 ≥ 起跳窗口 + 反应余量**（§3.4 已给推算，此处为结论）：全清晰下限 **≥2.3 m**（follow 1.98 m / listen 2.28 m 取上界），`≤18 m 全清晰` 现值远超需求 → **距离不是瓶颈，「该在哪一段点」的锚点才是**。方案 B 的 `VISUAL_FLOW_GAIN` 不放大 pickup 相对推进（石头绑判定 `t`），故该米数不随提速漂移。

**新增「起跳标线」HUD/3D 轻提示（补瓶颈）**：

### 10.3 单跳 / 二段跳在 3D 里两级可区分（0 新增 mesh）

- 全部走 `scene3d.jsx:257` 现成 `k.lift` y 通道 + 已有 `rotation` / 接地阴影；`KART_KEYS` 加 `hop/airMax`（§5.2，只读中性字段，`GATE_KEYS` 三键不动、B8 零触碰）。
- **单跳 `hop=1`**：单峰抛物线，峰值 0.55 m，阴影收缩一次。
- **二段跳 `hop=2`**：`p≈0.5` 处叠加第二次抬升脉冲（双峰，峰值 0.85 m）+ 车尾一小簇纸屑 + 极轻前倾（`rotation.x ≤2°`）+ 阴影二次收缩，形成「顿一下再往上」。

- **与 `hold` 冻结区分**：`hold`（`race.js:631-641` 3 秒冻结 odo）用「贴地静止 + 听音标识 + 去饱和」，跳跃态用「离地上冲 + 不去饱和」（§5.4），二者不可混淆。
