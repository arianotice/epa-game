## §1 撞石次数上限裁定（用户最终拍板：每局 ≤2 次）

### §1.1 问题与口径收敛

用户原话（§0.3 逐字）：「限定每局撞到石头的次数不超过2次」。

「撞石头」在本作中 = 触发 `openQuiz("rock")` 一次 = 弹一道额外听辨题。故 **撞石次数可直接用现有 `quizReasons.rock` 计数**，无需新增统计字段。

三候选（质量线 R4 实测，v1.0 留痕）：

| 候选 | 分母 | 上限 | 评价 |
| --- | --- | --- | --- |
| A | 闸门题数 `G = laps × commits.length = 2 × 2 = 4` | `⌊4/6⌋ = 0` | 机制空转：与用户「石头要被看见、可跳过」自相矛盾 |
| B | 含额外惩罚题的**实际**总题数（最坏局实测 24） | 4 | 语义最贴近，但**分母含实际撞石次数 → 循环自指**，不可验收 |
| C | 石头总数 `8 × 2 = 16` | `⌊16/6⌋ = 2` | 分母是「投放个数」而非「题数」，语义错配 |

现状最坏局 `quizReasons.rock = 7`（normal 0/5/3/6）**已超任一合理口径**。

> **用户最终拍板（取代下方 v1.0 推荐 R）**：分母歧义**不再求解** —— 直接收敛为**整数硬上限：每局撞到石头次数 ≤ 2 次**（`∀ 单局 quizReasons.rock ≤ 2`，100% 局次满足）。
> `1/6` **仅作为「石头应稀疏」的设计意图保留，不再单独设比例阈值**；原 `N_budget = 24 / H_max = ⌊24/6⌋ = 4` **作废**（保留作决策留痕，见 §1.2）。
> 由此，质量线「1/6 分母口径」这一最高优先待裁决项**已由用户拍板关闭**；验收阈值现可直接定义为整数 2。

### §1.3 边界裁定

| 边界 | 裁定 |
| --- | --- |
| 题目数 `< 6` | **不再适用**（`1/6` 退为设计意图、无分母即无「<6」边界）。替代保障：石头总数 ≤2 颗 + 每颗须单跳必过（§1.5 / §2.4）。v1.0 曾定「`H_max=⌊N/6⌋=0` → 禁生成可碰撞石头」，作留痕 |
| 石头与闸门**同里程重叠** | **禁止**（见 §6 排除区间） |
| 石头出现在**分叉决策窗口**内 | **禁止**；决策窗口内为「选道态」，点击只能有一个语义 |
| 「不能随机出现逼用户撞上」 | 每颗石头须同时满足：① 提前可见 ≥ `T_visible = 1.6s`；② 有效跳跃窗口 ≥ `T_jump = 0.45s`（F12 实测基线）；③ 生成点距最近闸门 ≥ `span + merge`；④ 成功跳跃即不判碰撞；⑤ 禁止「生成即在碰撞点」的石头；⑥ **单跳必过 100%（最高优先，§2.4）** |
| 「石头数」 vs 「撞石数」 | **二者均受硬约束且必须分开定义**：撞到次数 ≤2，且推荐石头生成总数 ≤2 颗（§1.5）；禁止互相换算、禁止用计数封顶制造假障碍 |

### §1.4 口径变更后的遗留说明

v1.0 的 `N_budget = 24` 静态预算风险（提速 / 题型变化导致总题数上界漂移）**随分母口径废弃而消失**：现行方案不再依赖任何题数统计，改由「石头生成总数」直接封顶，抗漂移。新引入的风险转为「石头总数与假障碍」的取舍，见 §1.5。

### §1.5 「石头生成总数」与「撞到次数」口径分离 + 推荐

两个量必须**分开定义、分别验收**，禁止混用：

| 量 | 定义 | 约束 |
| --- | --- | --- |
| **石头生成总数** `N_stone` | `buildField()` 一局投放到赛道上的可碰撞石头个数（现状 8 颗 × 2 圈 = 16 次遭遇机会，F9） | **推荐 ≤2 颗 / 局** |
| **撞到次数** `quizReasons.rock` | 触发 `openQuiz("rock")` 的次数 | **硬上限 ≤2 次 / 局（100% 局次）** |

> **推荐 A（主理人倾向，design 侧采纳）：每局石头总数 ≤2 颗。**
> 理由：
> ① `N_stone ≤ 2` 时 `quizReasons.rock ≤ 2` **天然成立**，无需额外拦截逻辑，验收退化为单条「石头数 ≤2」；
> ② 现状 16 颗 / 最坏局撞 7 次，收敛幅度 87.5%，一次性消解「撞石过多」与「连续弹题打断节奏」；
> ③ 与 §1.3「每颗石头提前可见、单跳必过」一致 —— 石头**少而每颗都真实、可躲、有反馈**，正合用户「石头须被看见、不能随机逼撞」；
> ④ 与 180s 余量（R1，仅 5.43s）友好：撞石额外题最多 2 次；
> ⑤ 无「封顶后石头失效」的逻辑分支，状态机更简单，门控断言更少。
> 落地：`buildField()` 的 rock 循环由 8 颗改为 ≤2 颗（gem 10 颗不动）；两圈共用 field 时按**每局**而非每圈计数，避免 `2×2=4` 颗溢出；`settle()` 重定位上限随之复核。

> **备选 B（不推荐，仅登记备查）：生成稍多 + 碰撞计数封顶 2。**
> 做法：石头仍生成较多（如 4–6 颗），但 `quizReasons.rock` 达到 2 后，后续石头不再触发 `openQuiz("rock")`。
> **决定性缺陷**：封顶之后的石头变成**「假障碍」** —— 视觉上存在、玩家仍需躲，但撞上后无任何后果（不弹题、不计数、不反馈），形成「看起来危险其实无害」的**欺骗性反馈**；直接违背用户「石头须被看见、跳跃躲过」的诚实交互前提，并让小学六年级玩家习得「后面石头可以不管」的错误规则（**主导策略 + 认知不一致**，设计理论红线）。故**不采纳**。

> **已裁定照准（v1.3）**：推荐 A 的「每局石头总数 ≤2 颗」照准执行。此为**主理人加的额外保险，用户可单独撤销**（该注明保留）；撤销不影响 §1.1「每局撞到 ≤2 次」硬上限。见 §9 P9。

## §2 跳跃交互裁定

### §2.1 用户已拍板（本裁定书不再推荐替代方案）

- **【最高优先硬验收 · 单跳必过 100%】** 用户原话（§0.3 逐字）：「要么你就确保用户只需点击一次空格键或者点击"跳跃"就能完美刚好跳过石头的高度」。裁定：**一次空格或点「跳跃」必能 100% 完美跳过高过石头**，绑定**单次输入**，**不绑定双击**；这是本裁定书**最高优先验收项**，任何机制不得让「必须会双击才能过」成为前提。
- 一下 = 普通跳；**约 260ms 内第二击** = 在首跳基础上再往上跳一点（**更高余量**），**同时保持前行（水平速度不变）**；触屏同规则。
- 禁止浏览器原生 `dblclick`（会引入 ~300ms 双击延迟且不可控）。
- 首击**立即**起跳，不等第二击判定。
- **二段跳只作为更高余量**：保留上一轮已拍板的增强与时机余量，**不得成为单跳能过的前提**。
- **实现载体归 engineering-lead 的 E1 定夺**（§2.3）；裁定书**只保留交互口径**：首击立即起跳、约 260ms 内第二击追加抬升、落地复位段数、水平速度恒定、单跳必过 100%（不作门槛）；**复活 `hopWindow` / 新建状态机 / 收窄 `air` 判定三选一由工程层决定，裁定书不指定**。

## §3 分叉 UX 五阶段时序裁定

### §3.1 状态互斥总原则

> **任意时刻，一次点击只有一个语义。**
> 定义两个互斥区间：
> - **选道态 `DECIDE`**：`odo ∈ [gate.line - span*L, gate.line + merge*L]`（= **span + merge**，**绝对里程**，F8）。此区间内点击 = 选左 / 右半屏；**跳跃输入屏蔽**；**禁止生成石头**。
> - **可跳跃态 `HOP`**：一局中所有 `DECIDE` 区间之外的单车道直行段。此区间内点击 = 跳；**左右半屏选道输入屏蔽**；石头只在此区间生成。
>
> 键盘 `←/→` 与 `Space` 天然不冲突，但为保持 HUD 语义一致，仍按上述区间只提示对应操作。

### §3.2 五阶段时序（每一门重复一次）

```
[T0] 单车道直行 · HOP 态
      HUD：「前方有石 · 点一下跳过去」（仅在石头进入 T_visible 时出现）
      石头仅在此区间生成（且满足 §1.3 / §6 排除）
        │
        │  距 gate.line = span*L  → 进入 DECIDE
        ▼
[T1] 分叉张开（张开）
      赛道几何由 1 条渐变为 2 条真实分支（用户硬需求：必须做真实分叉，
      不是「视觉贴牌」）。左右分支在空间中真实分离，车可被开进去。
      HUD 切为：「听一听 · 点左 / 右半屏选道」   ← DECIDE 开始，跳跃屏蔽
        │
        ▼
[T2] 左右分支挂音频卡片（选道依据）
      每侧分支入口挂一张「音频卡片」：播放按钮 + 该分支对应的单词音频。
      ★ 卡片只承载「可点播放」这一交互，不显示答案、不显示对错、
        不显示 correctLateral / spoken / left / right 等字段名（对齐 H5 答案零泄露）。
      ★ 卡片上的 IPA / 中文一律 DOM textContent 后期准确合成，
        禁止 AI 直渲 / 禁止烘焙进 3D 贴图位图（防乱码）。
        ★ 保持 D3「听音选车道」：不得让视觉提示退化为看图选车道；
          S1 阶段两块牌零文本、同形同色同帧出现（沿用 hud-ux-spec.md 口径）。
        │
        ▼
[T3] 用户移动选道 → 判定（选道态）
      输入：点左 / 右半屏（触屏优先）+ 键盘 ← / → 并存。
      车真实驶入对应分支；到 gate.line 由 hitsLane() 判定。
      判定后 → 反馈（不泄露另一分支答案）。
        │
        ▼
[T4] 分叉渐变闭合（merge 段）
      两条分支平滑收束回单车道，闭合过程 ≥ merge 对应里程，避免瞬切。
      HUD 提示淡出；仍属 DECIDE，禁石、屏跳。
        │
        │  odo > gate.line + merge*L  → 回到 HOP
        ▼
[T5] 单车道 · HOP 态 → 下一题（下一门回到 T0）
```

### §3.4 左右分支音频标注落实（防乱码）

- 音频卡片本体为 **DOM 层**（现有 `#signs` / `#sign-l` / `#sign-r` 体系可复用），叠在 3D 世界空间投影位置之上，不进 WebGL 纹理。
- 单词 / IPA / 中文一律 `textContent` 写入；IPA 显示唯一权威 `IPA_DISPLAY`（美式）；`sym` 仅作英式稳定数据键，**绝不出现在 UI 文本与键位**，尤其不动 `story.js` 的 `seen[p.sym]`。
- 字体：使用已烘焙的 IPA 字形 Web Font（`woff2` + `unicode-range`），缺失字形回退到 SVG 字形，**不回退到图像生成**。
- 两侧卡片**同形、同色、同帧出现**（S1 中性牌口径），避免任何一侧「更显眼」造成视觉泄露。

### §3.5 提速与听音反应窗口 —— 方案 B 已定为默认

先讲清公式（方案 B 下更有利）：

- `span = forkSpan(diff, L) = diff.fork * diff.speed / L`（F8），分叉窗口**里程**长度 `= span * L = diff.fork * diff.speed`。
- 故名义时间窗口 `= (span*L) / diff.speed = diff.fork` 秒 → **3.6s（follow）/ 3.4s（listen），与 `diff.speed` 无关**。
- 提高 `diff.speed` 只会**线性拉长分叉的里程跨度**，**不缩短听音反应时间**；team-lead 补充输入 #2 中「提速会按 `forkSpan()` 线性改变窗口长度」指的是**里程**，不是时间。

> **方案 B（`VISUAL_FLOW_GAIN` 环境流速增益）= 本轮提速默认（已裁定，命名与美术线 / 工程线一致）**
> 判定层 `diff.speed` **260 / 300 不变**；提速只在**渲染 / 视觉层**做流动增益（镜头速度感、路面纹理流动、尾迹与粒子），**不写 `odo`、不写 `speedNow()`、不改 `finishTime`、不动 `span` / `g.line` / `judge()`**。
> 由此：① `span` 不变 → 分叉时间窗口恒为 `fork` 秒，**听音反应窗口零压缩**；② 既有**写死 `260/300` 的断言不会被撞**；③ 风险由「提速挤掉反应时间」**降级为「补防视觉增益泄漏到判定层」**（R13）。
> 回应「3D 车速太慢、不够丝滑」由视觉层承担，物理计时不变 → **`≤180s` 门槛不变，最慢 `174.57s` 仅 `5.43s` 余量的风险仍须保留**（R1）。

**历史留痕（非候选项 · P3 已裁定关闭）**

- 早期「方案甲（`DECIDE` 内锁 `mul=1`）」「方案乙（`span` 按 `max(speedNow)` 预估）」均为 v1.0 探索口径，**已归档、不再是待定项**；提速唯一执行方案为**方案 B（`VISUAL_FLOW_GAIN` 环境流速增益）**，判定层 `speed` 260/300 不变。
- 保留一条设计约束：`BOOST / TURBO` 动态倍率不得泄漏进 `DECIDE` 区间的判定里程基准（与 R13 同源），仅为工程检查项，不构成第二方案。

> 另：`hud-ux-spec.md` 的 `D_preview = span·L + 0.5·preview·speed`（follow 5.70s / listen 5.40s）继续用名义 `diff.speed`，方案 B 下与本裁定不冲突。

## §6 里程互斥与石头生成 —— 修正 `blocked()`

### §6.1 现状不成立（F7 / F8）

`blocked()`（`race.js:114-120`）只排除起点 `0.04·L` 与各 `commitT` 附近 `\|t - commitT\| < 0.04`（≈ 0.04 比例 ≈ 770.2m 口径，且用**归一化 t**）。而真实分叉窗口是 **`[gate.line - span*L, gate.line + merge*L]`**（`race.js:337-340`、`:365-369`，**绝对里程**），长度 = **span + merge**（≈ follow 1475.1m / listen 1559.1m）。

实测：第 5 颗石头 `t ≈ 0.6288` **已落入 listen 窗口 `[0.627, 0.708]`** → 出现「选道态里要跳石头」的语义冲突，里程互斥未成立。

### §6.2 修正裁定（按 `g.line` 绝对里程区间）

> **排除区间 = span + merge，且必须按 `g.line` 绝对里程判定。`blocked()` 改为：若石头的绝对生成里程落在任一门的 `[g.line - span*L, g.line + merge*L]` 内，即 `true`。**

```
blocked(odo_stone) =
    近起点(<0.04·L)  OR
    ∃ gate g: odo_stone ∈ [g.line - span*L, g.line + merge*L]
```

- **与 §3.1 的 `DECIDE` 定义同源**：`race.js:337-340` 用的就是绝对 `gate.line`；`g.line = player.startOdo + g.lineT * L` 按圈展开，**不使用归一化 `t` 环绕取模**，避免两圈同 `commitT` 串味（对齐 `hud-ux-spec.md` 两圈防串口径）。
- `span = forkSpan(diff, L) = diff.fork * diff.speed / L`；`merge = TUNING.mergeDt`（`race.js:8-9`）。**方案 B 下 `diff.speed` 260/300 不变 → `span` 不变**（§3.5）。
- **提速联动（方案 B 下弱化）**：`span` 与 `diff.speed` **线性正比**（F8）；若将来真改判定层速度，排除区间的**里程**随之变长，`blocked()` 必须用**运行时计算值**，禁止硬编码 `0.04`（这正是当前 bug 根因）。时间窗口恒为 `diff.fork` 秒，见 §3.5。
- `settle()`（`race.js:121-126`）已在 `blocked()` 时按 `+0.012` 最多 8 次重定位；修正排除区间后需复核 8 次是否够（窗口变长 → 可能需提高上限或改二分），**列为实现检查项**。
- 石头只能生成在 **`HOP` 单车道直行段**；`DECIDE` 内零石头、零跳跃输入、零左右选道之外的语义。
- **数量联动**：修正排除区间后仍须满足「每局石头总数 ≤2 颗」（§1.5），两者是**与**关系，不是替代关系。

## §7 NPC「像真人在开」—— 可观测行为清单与量化验收（写死）

用户诉求（§0.3 逐字）：「NPC卡丁车要确保看起来像真人驾车，不要龟速或者扎堆」。裁定方向：**不是让 NPC 更强，而是让 NPC 不整齐、不龟速、不扎堆、有反应**；且**不得改变 `place` 判定与 `finishTime` 基线**。

| # | 可观测行为 | 定义 | 量化验收判据（`headless` 采样 `odo / lateral / v`） |
| --- | --- | --- | --- |
| N1 | 错峰 / 不扎堆 | 发车与全程位置不重合成一列 | `t=0` 时任意两 NPC `\|odo_i - odo_j\| ≥ 0.03·L`；全程同一 `0.1·L` 区段内 NPC 数 `≤ 2` 的时间占比 `≥ 95%` |
| N2 | 微速差 | 各车目标速度不一致且缓慢波动 | `v_i / v_base ∈ [0.94, 1.06]`，相邻 1s 变化 `≤ 0.02`；任意 1s 窗内 `v_i` 两两不全等 |
| N3 | 偶发换道 | 会主动换线，但不在决策窗口添乱 | 每圈每 NPC `1–3` 次；**100%** 落在 `HOP` 单车道段，`DECIDE` 区间内换道次数 `= 0` |
| N4 | 不完美走线 | 不沿绝对理想线 | `lateral` 叠加低频噪声，标准差 `∈ [0.02, 0.06]`，幅度 `≤ 0.05` |
| N5 | 被超车反应 | 玩家超越后有「人」的回应 | 玩家超越后 `[0.8s, 1.5s]` 内，该 NPC 出现一次 `Δv ≥ 0.03` 或一次换道意图；命中率 `≥ 70%` |
| N6 | 不扎堆（综合） | 视觉上不抱团 | 任意时刻任意两 NPC 的 `(Δodo, Δlateral)` 同时 `< (0.02·L, 0.15)` 的持续时间 `≤ 0.5s` |
| N7 | 不破坏基线 | 拟人化不得影响结果 | 11 场 headless 的 `finishTime` / `place` 与改动前逐项一致（对齐既有门控口径） |
| **N8** | **速度下限（不得龟速）** | NPC 不得明显慢于玩家，避免「像静止路障」 | 全程 `v_i ≥ 0.94 · v_player_now` 且 `v_i ≥ 0.90 · v_base`；「明显慢于玩家」（`v_i < 0.90 · v_player_now`）的**持续时间 = 0**；玩家 `BOOST / TURBO` 期间按玩家**名义速度**折算，不得因玩家瞬时加速把 NPC 误判为龟速 |

> **「像真人驾车」可观测项写死**：N1 错峰 / N2 微速差 / **N8 速度下限** / N3 偶发换道 / N4 不完美走线 / N5 被超车反应 / N6 不扎堆 / N7 不破坏基线 —— **共 8 项，逐项硬 `chk`**，不接受「视觉上差不多」的主观判定；任何一项不达标即判 FAIL。
> **N8 阈值统一（v1.3 留痕）**：主理人裁定取**更严的 `0.94 · v_player_now`**（更贴合用户「不要龟速」），本裁定书 N8 **保持不变**；质量线断言已由 `0.9×` **收紧到 `0.94×`**（是收紧，不是放宽）。
> 实现提示：以上均可通过给 NPC 目标速度与 `laneTarget` 加**确定性种子噪声**实现，避免真随机导致门控不可复现；种子建议由 `mapId + raceId` 派生。
